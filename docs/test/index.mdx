Bun 自带一个高速、内置、兼容 Jest 的测试运行器。测试在 Bun 运行时中执行,支持以下特性。

- TypeScript 和 JSX
- 生命周期钩子
- 快照测试
- UI 和 DOM 测试
- `--watch` watch 模式
- `--preload` 脚本预加载

<Note>
  Bun 力求与 Jest 兼容,但并非所有功能都已实现。兼容性进度见[这个跟踪
  issue](https://github.com/oven-sh/bun/issues/1825)。
</Note>

## 运行测试

```bash terminal icon="terminal"
bun test
```

使用类 Jest 的 API 以 JavaScript 或 TypeScript 编写测试。参见[编写测试](/test/writing-tests)。

```ts math.test.ts icon="/icons/typescript.svg"
import { expect, test } from "bun:test";

test("2 + 2", () => {
  expect(2 + 2).toBe(4);
});
```

测试运行器会递归搜索工作目录中匹配以下模式的文件:

- `*.test.{js|jsx|ts|tsx|mjs|cjs|mts|cts}`
- `*_test.{js|jsx|ts|tsx|mjs|cjs|mts|cts}`
- `*.spec.{js|jsx|ts|tsx|mjs|cjs|mts|cts}`
- `*_spec.{js|jsx|ts|tsx|mjs|cjs|mts|cts}`

要过滤要运行的_测试文件_集合,向 `bun test` 传入额外的位置参数。路径匹配任一过滤器的测试文件都会运行。过滤器通常是文件名或目录名;尚不支持 glob 模式。

```bash terminal icon="terminal"
bun test <filter> <filter> ...
```

要按_测试名称_过滤,使用 `-t`/`--test-name-pattern` 参数。

```sh terminal icon="terminal"
# run all tests or test suites with "addition" in the name
bun test --test-name-pattern addition
```

要在测试运行器中运行特定文件,确保路径以 `./` 或 `/` 开头,以便与过滤器名区分。

```bash terminal icon="terminal"
bun test ./test/specific-file.test.ts
```

默认情况下,测试运行器在单个进程中运行所有测试:先加载所有 `--preload` 脚本(见[生命周期](/test/lifecycle)),然后在一个共享全局中运行每个文件。传 [`--parallel`](/test/parallel) 可将文件分散到各个 CPU 核心执行。测试失败时,测试运行器以非零退出码退出。

## CI/CD 集成

`bun test` 支持多种 CI/CD 集成。

### GitHub Actions

`bun test` 会自动检测是否运行在 GitHub Actions 中,并直接向控制台输出 GitHub Actions 注解。

无需配置,只要在 workflow 中安装 `bun` 并运行 `bun test` 即可。

#### 如何在 GitHub Actions workflow 中安装 bun

要在 GitHub Actions workflow 中使用 `bun test`,添加以下步骤:

```yaml title=".github/workflows/test.yml" icon="file-code"
jobs:
  build:
    name: build-app
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Install bun
        uses: oven-sh/setup-bun@v2
      - name: Install dependencies # (assuming your project has dependencies)
        run: bun install # You can use npm/yarn/pnpm instead if you prefer
      - name: Run tests
        run: bun test
```

### JUnit XML 报告(GitLab 等)

要写出 JUnit XML 报告,传 `--reporter=junit` 并配合 `--reporter-outfile`。

```sh terminal icon="terminal"
bun test --reporter=junit --reporter-outfile=./bun.xml
```

`bun test` 仍会照常写入 stdout/stderr,并在运行结束时把 JUnit XML 报告写入指定路径。

JUnit XML 是 CI/CD 流水线中常用的测试结果报告格式。

## 超时

使用 `--timeout` 参数指定_每个测试_的超时时间(毫秒)。测试超时时,Bun 将其标记为失败。默认值为 `5000`。

```bash terminal icon="terminal"
# default value is 5000
bun test --timeout 20
```

## 并发测试执行

跨 CPU 核心运行测试**文件**见 [`--parallel`](/test/parallel)。以下参数控制的是单个文件_内部_测试的并发。

默认情况下,Bun 在每个测试文件中按顺序运行所有测试。并发执行会并行运行异步测试,从而加速彼此独立的测试套件。

### `--concurrent` 参数

使用 `--concurrent` 参数让各文件内的所有测试并发运行:

```sh terminal icon="terminal"
bun test --concurrent
```

启用该参数后,所有测试都会并行运行,除非用 `test.serial` 标记。

### `--max-concurrency` 参数

使用 `--max-concurrency` 参数控制同时运行的最大测试数:

```sh terminal icon="terminal"
# Limit to 4 concurrent tests
bun test --concurrent --max-concurrency 4

# Default: 20
bun test --concurrent
```

该限制有助于防止大量并发测试耗尽资源。默认值为 20。

### `test.concurrent`

标记单个测试并发运行,即使未使用 `--concurrent` 参数:

```ts title="math.test.ts" icon="/icons/typescript.svg"
import { test, expect } from "bun:test";

// These tests run in parallel with each other
test.concurrent("concurrent test 1", async () => {
  await fetch("/api/endpoint1");
  expect(true).toBe(true);
});

test.concurrent("concurrent test 2", async () => {
  await fetch("/api/endpoint2");
  expect(true).toBe(true);
});

// This test runs sequentially
test("sequential test", () => {
  expect(1 + 1).toBe(2);
});
```

### `test.serial`

强制测试按顺序运行,即使启用了 `--concurrent` 参数:

```ts title="math.test.ts" icon="/icons/typescript.svg"
import { test, expect } from "bun:test";

let sharedState = 0;

// These tests must run in order
test.serial("first serial test", () => {
  sharedState = 1;
  expect(sharedState).toBe(1);
});

test.serial("second serial test", () => {
  // Depends on the previous test
  expect(sharedState).toBe(1);
  sharedState = 2;
});

// This test can run concurrently if --concurrent is enabled
test("independent test", () => {
  expect(true).toBe(true);
});

// Chaining test qualifiers
test.failing.each([1, 2, 3])("chained qualifiers %d", input => {
  expect(input).toBe(0); // This test is expected to fail for each input
});
```

## 重试失败的测试

使用 `--retry` 参数自动重试失败的测试,最多重试指定次数。如果测试失败后在后续尝试中通过,Bun 会报告其通过。

```sh terminal icon="terminal"
bun test --retry 3
```

单个测试的 `{ retry: N }` 会覆盖全局 `--retry` 值:

```ts
// Uses the global --retry value
test("uses global retry", () => {
  /* ... */
});

// Overrides --retry with its own value
test("custom retry", { retry: 1 }, () => {
  /* ... */
});
```

也可以在 `bunfig.toml` 中设置:

```toml title="bunfig.toml" icon="settings"
[test]
retry = 3
```

## 重复运行测试

使用 `--rerun-each` 参数把每个测试运行多次,用于暴露不稳定或非确定性的测试失败。

```sh terminal icon="terminal"
bun test --rerun-each 100
```

## 随机化测试执行顺序

使用 `--randomize` 参数以随机顺序运行测试,有助于发现依赖共享状态或执行顺序的测试。

```sh terminal icon="terminal"
bun test --randomize
```

使用 `--randomize` 时,Bun 会在测试摘要中显示随机化种子:

```sh terminal icon="terminal"
bun test --randomize
```

```txt
# ... test output ...
 --seed=12345
 2 pass
 8 fail
Ran 10 tests across 2 files. [50.00ms]
```

### 用 `--seed` 复现随机顺序

使用 `--seed` 参数指定随机化种子,在调试顺序相关失败时复现相同的测试顺序。

```sh terminal icon="terminal"
# Reproduce a previous randomized run
bun test --seed 123456
```

`--seed` 隐含 `--randomize`,无需同时指定。相同种子总是产生相同的测试执行顺序。

## 用 `--bail` 中止

使用 `--bail` 参数在出现指定数量的测试失败后中止测试运行。默认情况下,Bun 会运行所有测试并报告所有失败,但在 CI 中早停以降低 CPU 占用可能更合适。

```sh terminal icon="terminal"
# bail after 1 failure
bun test --bail

# bail after 10 failure
bun test --bail=10
```

## Watch 模式

与 `bun run` 一样,`bun test` 接受 `--watch` 参数来监视变更并重新运行测试。

```bash terminal icon="terminal"
bun test --watch
```

## 生命周期钩子

Bun 支持以下生命周期钩子:

| 钩子         | 说明                 |
| ------------ | -------------------- |
| `beforeAll`  | 在所有测试前运行一次。 |
| `beforeEach` | 在每个测试前运行。     |
| `afterEach`  | 在每个测试后运行。     |
| `afterAll`   | 在所有测试后运行一次。 |

钩子可以定义在测试文件内,或定义在单独文件中并通过 `--preload` 参数预加载。

```sh terminal icon="terminal"
bun test --preload ./setup.ts
```

参见[生命周期](/test/lifecycle)。

## Mock

使用 `mock` 函数创建 mock 函数。

```ts title="math.test.ts" icon="/icons/typescript.svg"
import { test, expect, mock } from "bun:test";
const random = mock(() => Math.random());

test("random", () => {
  const val = random();
  expect(val).toBeGreaterThan(0);
  expect(random).toHaveBeenCalled();
  expect(random).toHaveBeenCalledTimes(1);
});
```

也可以使用 `jest.fn()`,行为完全相同。

```ts title="math.test.ts" icon="/icons/typescript.svg"
import { test, expect, mock } from "bun:test"; // [!code --]
import { test, expect, jest } from "bun:test"; // [!code ++]

const random = mock(() => Math.random()); // [!code --]
const random = jest.fn(() => Math.random()); // [!code ++]
```

参见 [Mocks](/test/mocks)。

## 快照测试

`bun test` 支持快照测试。

```ts title="math.test.ts" icon="/icons/typescript.svg"
// example usage of toMatchSnapshot
import { test, expect } from "bun:test";

test("snapshot", () => {
  expect({ a: 1 }).toMatchSnapshot();
});
```

要更新快照,使用 `--update-snapshots` 参数。

```sh terminal icon="terminal"
bun test --update-snapshots
```

参见[快照](/test/snapshots)。

## 大型代码库

对于包含数千个测试文件的套件,`bun test` 提供了多种可叠加的手段:worker 进程、隔离级别、跨机器分片和按时长感知的调度。[并行与隔离测试运行](/test/parallel)对每一项都有深入说明。下面按收益大致排序,介绍它们如何配合:

**1. 用满每个核心:[`--parallel`](/test/parallel#--parallel)。** 每核一个 worker,文件逐个分发。

**2. 决定需要多少隔离。** `--parallel` 为每个文件提供全新全局环境,这是安全默认值,也是 Jest/Vitest 的做法。如果你的文件之间不互相泄漏状态(在共享单一全局的普通 `bun test` 下已经通过),[`--parallel --no-isolate`](/test/parallel#every-file-is-isolated-unless-you-opt-out) 能让每个 worker 只求值一次导入和预加载脚本,而不是每个文件一次。对由大量小文件组成的套件,这是最大的单项收益。参见[对比说明](/test/parallel#how-it-compares)。

**3. 跨机器拆分:[`--shard=i/n`](/test/parallel#splitting-a-suite-across-ci-machines-with---shard)。** 确定性分片,无需协调器。每个 CI 作业运行一个分片,每个分片本地仍可用 `--parallel`。

**4. 按时长而非数量均衡:[`--timings`](/test/parallel#balancing-with---timings)。** 依据记录的耗时,Bun 会切分分片,使各分片总耗时大致相同。切分采用最长处理时间优先策略,但会把路径相邻的文件保持在一起,让 worker 的模块缓存保持热度。每个 worker 先运行其最慢的文件,空闲 worker 会"偷走"剩余最慢的文件。这样,某个恰好最后才开始的长文件不会拖住整体运行。

**5. 自动保持时长数据新鲜:`--update-timings`。** 每个分片写出其运行文件的耗时,下一次运行读取全部数据。在 GitHub Actions 中形如:

```yaml title=".github/workflows/test.yml" icon="github"
jobs:
  test:
    strategy:
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install
      # last successful run's per-shard timings (nothing on the very first run)
      - uses: actions/cache/restore@v4
        with:
          path: .bun-test-timings
          key: bun-test-timings-${{ github.run_id }}
          restore-keys: bun-test-timings-
      - run: |
          bun test --parallel --shard=${{ matrix.shard }}/4 --update-timings \
            --timings=.bun-test-timings/next/${{ matrix.shard }}.json \
            $(ls .bun-test-timings/*.json 2>/dev/null | sed 's/^/--timings=/')
      - uses: actions/upload-artifact@v4
        with:
          name: timings-${{ matrix.shard }}
          path: .bun-test-timings/next/${{ matrix.shard }}.json
  save-timings:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          pattern: timings-*
          path: .bun-test-timings
          merge-multiple: true
      - uses: actions/cache/save@v4
        with:
          path: .bun-test-timings
          key: bun-test-timings-${{ github.run_id }}
```

每个分片必须读取_同一组_时长文件,各分片相加才能覆盖整个套件。这就是为什么每次运行要读取上一次运行的文件(从缓存恢复),并把本次输出写到兄弟分片不会读取的位置(上面的 `next/`)。如果第 2 步适用于你,在 `bun test` 命令行中加上 `--no-isolate`。

**6. 文件内部:[`test.concurrent`](#concurrent-test-execution)** 适用于大量时间花在 await 上的 I/O 密集型测试。

## AI Agent 集成

将 Bun 测试运行器与 AI 编码助手配合使用时,可以启用更安静的输出:保留失败细节,去掉其余噪音。

### 环境变量

设置以下任意环境变量即可启用 AI 友好输出:

- `CLAUDECODE=1` - 适用于 Claude Code
- `REPL_ID=1` - 适用于 Replit
- `AGENT=1` - 通用 AI agent 标志

### 行为

Bun 检测到 AI agent 环境时:

- 只详细显示测试失败
- 隐藏通过、跳过和 todo 测试的指示
- 摘要统计保持不变

```bash terminal icon="terminal"
# Example: Enable quiet output for Claude Code
CLAUDECODE=1 bun test

# Still shows failures and summary, but hides verbose passing test output
```
